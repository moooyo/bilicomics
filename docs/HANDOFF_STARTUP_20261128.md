The application, complete launcher, package verifier, real host ELF integration, and desktop Reader checks passed. The official ARM builder and byte verifier passed once, but the outer runner failed to export that ZIP. A corrected export rerun stopped at the shared test host's disk reserve. ## What changed

- The old required startup read could publish both command and completion receipts within budget but exit before the launcher accepted them; the launcher would reject the read before checking the receipts. This failure class was reproduced deterministically. A separate failed launch produced neither receipt and remains unexplained. Do not treat this fix as an explanation of all startup failures.
- The [launcher](../packaging/kindle/launch.sh) and the [native owner and receiver](../src/native_presentation/portrait_writer/startup_read.rs) now use an anonymous, single-use result channel for the first required display snapshot. The same-executable owner supervises its private group, seals a bounded body only after successful sampling and EOF within two seconds, then retires its own subtree and revokes its exact grant. The launcher can collect a sealed receipt within three seconds of the same start, not an extra second of sampling. It checks the real child status and parses the snapshot before publishing it. Unproven retirement keeps the lock; no retry or fallback bypasses that gate.
- The receiver closes the race between observing a zombie and reading its pinned `/proc` record. Only `ENOENT` or `ESRCH` during that read permits one more existence check; that check must prove the PID absent. A live or reused identity, invalid record, or other I/O error still refuses. Startup admission still passes through the native power relay, so a queued sleep or USB event precedes display takeover. The optional blanket read, portrait publication, wake and framebuffer-capability paths keep their separate guards.
- The [development verifier](../scripts/verification/verify_dev_payload.py) excludes only the two exact startup-internal launcher commands from its ordinary UI invocation check. It still requires one unchanged ordinary invocation, validates source/staging/archive bytes and CRC, and admits no additional model/firmware pair. An unexpected portrait target type can no longer abort independent cleanup in the exit trap; the saved exit status is preserved and unexpected directories are not recursively removed.
