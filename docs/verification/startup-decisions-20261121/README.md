# Startup decisions: what to keep, what to build next

**Keep the last verified Scribe installation. The primary metric is [ordinary native card release to the first Shelf render](../../STARTUP_AND_SLEEP.md#primary-startup-metric-first-shelf-render), not cover completion or clickability.** The [historical desktop interactive baseline](../startup-interactive-shelf-20261121/README.md) measured a median upper bound of 180.376 ms with six successful clicks. The historical results below retain their original endpoints. Neither that desktop baseline nor the complete-frame or launcher studies establishes a gain on the new primary metric.

## Implementation and deployment

The [two initial physical baseline launches](../startup-interactive-kindle-20261121/README.md#scribe-results) took approximately **6.451 s** and **6.727 s** to the first Shelf software render on Scribe. Their trace headers arrived **3.68–3.77 s** after card release. The [independent November 22 A/A](../startup-clock-aa-20261122/README.md) split that interval on one clock. All ten identical-launcher visits reached the normal Shelf and returned native control. Excluding two warmups, the eight measured launches had a median card-release-to-render time of **6.324215–6.325388 s**. The second launch was faster in 2/4 pairs (median second minus first: −42.734 to −40.089 ms), not a fixed first-launch advantage. Neither baseline demonstrates a speedup or changes the A/B rollout decisions.

## Do not implement as product optimizations

- **Moving the cover copy to a worker or decoding PNG directly into UI pixels:** respectively [1/6](../startup-cover-worker-20261121/README.md) and [0/6](../startup-direct-png-20261121/README.md#results) unambiguously earlier complete desktop Shelves. Do not ship those prototypes on that evidence. Neither experiment tested presenting an actionable Shelf before its covers finish.
- **A shorter desktop bootstrap timer or a private renderer fork:** the guarded [desktop prototype](../startup-desktop-wake-20261121/README.md#paired-results) really advanced the first complete window by 56.338 ms at the paired median. It relied on a per-window successful software submission that the pinned backend does not expose publicly. Revisit only with a supported equivalent. Do not port this to Kindle, which already has native first-SEND admission.
- **Skipping or deferring database cleanup, removing protection reads, or relaxing durability:** the *same* binary spent 7.481 ms on original fixture text and 0.490 ms on the product's persisted text. The 24-byte formatting difference caused a one-row rewrite only on the former; both deleted zero rows. The [six-pair difference](../startup-cache-maintenance-20261121/stages.md) is not product speedup. Larger real libraries are a separate question, not a reason to weaken the policy.
- **Reviving the [native-query helper](../../NATIVE_QUERY_STARTUP_20261117.md) or [hidden-route refresh prototype](../../STARTUP_SEQUENCE_PERFORMANCE_20261117.md#decision), shortening the two-second power-observer settle, bypassing the shared Library handler, or removing frame/driver checks:** no defensible endpoint gain warrants these changes. The accepted ordinary-Shelf route coalescing is not the rejected general hidden-route prototype.
- **Caching a live display permission or dropping apparently duplicate checks:** a permission can change between two reads, including during a getter. Keep both power and hardware observations, in-flight revocation, timeout and group retirement. The [display study](../startup-display-sampling-20261122/README.md) found a safe *parsing-only* alternative, but its 113.369 ns per already-read record on Linux does not justify deploying it for startup speed.

## Remaining work, in order

1. **Move the next offline comparison from the launcher to Shelf/cover ordering.** The [three poll-split visits](../startup-display-poll-20261122/README.md) found 81.5–90.1% of poll time before the helper observed EOF. After EOF each visit spent only 20.195–42.504 ms, not 100 ms, and not necessarily waiting on a child that had already exited. Do not change the poll slice, exit checks, ownership checks or the full observer settle. The median card-release-to-Shelf renderer interval was 6.401–6.403 s in this single arm, not a gain over the [earlier unsplit study](../startup-display-sampling-20261122/README.md). The next testable question is whether the same populated Shelf metadata can render before its cached covers attach. Check correctness and final covers on both fixture sizes first; this is not another pixel-copy or wake-delivery trial. Preserve loading feedback.
2. **Use the verified reversible harness for the next candidate.** The [new runner](../startup-shelf-ab-20261121/RUNNER.md) already completed 14 native-card visits without replacing the production application or document. Keep data isolated, rehearse changes off device, and acquire only for a ready visit. Do not reuse the [older harness](../../physical/startup-optimization-20261119/resume/rebuilt/device-pair.sh) that requires absence of the production installation.
3. **Judge candidates by the first Shelf render.** In the [detailed replay](../startup-display-sampling-20261122/DEVICE_REPLAY.md) the full display sample took 480 ms at the median; **410 ms was grant to parent-observed success**, not time in the getters. The [earlier replay](launcher-replay.md#measurements) also identified portrait publication (115 ms) and cover capability (85 ms); none is proven removable. Compare one change at a time from normal card release to render completion, and report SEND and any same-marker driver completion separately. Preserve startup feedback, native safeguards and eventual cover correctness. Neither software Ready nor a response to a later tap is the render endpoint.
