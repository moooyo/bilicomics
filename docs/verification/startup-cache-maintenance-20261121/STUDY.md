# Startup cache maintenance: separate normal writes from fixture effects

## Question

The [previous non-demo desktop control](../startup-direct-png-20261121/phase-profile.md) spent a median 7.512 ms in `state-cache-maintenance`. That interval covers an entire optional SQLite transaction, not just deleting files, making a write or waiting for the storage device. Identify the work before proposing a change. Do not mix these measurements with demo, signed-out, optical, Kindle or real-account timings.

The [ordinary seed writer](../startup-direct-png-20261121/make_fixture.py) already stores `catalog_cache_recency` for twenty comics. It uses Python's default JSON spacing. The product serializes a structured recency value to compact JSON, and its [conditional UPSERT](https://www.sqlite.org/lang_upsert.html) compares stored and proposed **text**. Equal parsed values need not be equal text. This is a source-derived hypothesis, not a measured cost. Missing records, evictions, lock contention and write failures are different cases.

## Comparison fixed before collecting timings

- Use one current Release executable in a private `test-env` Linux/X11 workspace, with the retained catalog and startup diagnostics, stock scheduling, an isolated network and an offline synthetic account. Do not access Kindle. Both inputs must contain the same 20 comics, two Shelf pages, the same ten visible covers and the same logical recency lists in the same order.
- **F (original fixture text):** keep the exact saved recency text from the established ordinary fixture. **R (product-written text):** run a separate copy of F through the actual product, reach Shelf, then exit cleanly. Copy only its persisted recency text to an otherwise equivalent seed, not its other preferences or application data. Compare parsed values and other input rows and qualify the exact byte difference. Neither condition changes application code. This is not a clean cache versus a missing row, an OS cold versus warm cache, or a proposed product speedup.
- Check the expected one-time update, without inferring it from a timer: the key must already exist in both inputs. With no actual reclamation, expect all four successful DELETE statements to affect zero rows; expect the recency UPSERT to affect one row on F and zero on R. If those predictions fail, retain and explain the observations rather than relabeling cases. An independently missing key, real evictions, and busy/error recovery need separate functional evidence; exclude them from the timing pairs.
- Exclude one warmup of each input, then retain six alternating FR/RF pairs without replacements, using a fresh private data copy and Xvfb for every launch. The worker's outer span and its inner stages use monotonic elapsed and same-thread CPU time; no fixed wall clock or artificial startup delay is needed. The route, ten real visible marker codes and normal exit are correctness checks, not full-window latency estimates. Record original failed attempts separately.
- For each attempt collect [direct row counts](https://www.sqlite.org/c3ref/changes.html) from the existing statements, observed stage durations, outcome, and busy-timeout restoration. Emit the aggregate **after** the transaction and the existing parent span, without extra SQL or logging inside the transaction. An affected-row count in a rolled-back transaction is not a committed change. Durations do not count disk writes or `fsync` calls.
- Compare the maintenance and commit spans within each pair before computing medians. Keep between-run variation, both order groups and the rest of the transaction visible. If an extra write is specific to the original fixture, retain production retention and durability and use product-written recency as the steady-state fixture moving forward. A residual cost in R is not proven avoidable; a product speed claim would require its own behavior-preserving candidate and end-to-end comparison.
