# Ordinary offline cache-maintenance profile

**Question:** how much of ordinary startup cache maintenance is spent in each measured operation when a semantically identical input does, or does not, cause the existing SQL upsert to change a recency row? This is one release executable and two input representations, **not two implementations**. It is not a display benchmark or evidence of a Kindle speedup.

## Input identity

Use `profile_runner.py` in a fresh private `test-env` workspace mounted as `/work` by `unshare --net /opt/kindle-toolchain/ubuntu-run`. The only network interface must be loopback. Copy the completed stock-renderer diagnostic release to `/work/study`, binding the copy to the build output with `cmp`: the same exact path serves all cases. Stage the newly built `/work/seed-profile` synthetic-only helper and the previously reviewed [fixture generator](../startup-direct-png-20261121/make_fixture.py), [ordinary Shelf helper](../startup-direct-png-20261121/ordinary_pairs.py), and its `desktop_pairs.py` import. Do not copy any old sample, input profile, or captured account data. Use the already qualified, in-process mock identity, production PNG writer, twenty distinct synthetic comics, and ten visible cover codes; every launch is `--offline`, never `--demo`. No shell, observer or application has a preload, fixed wall clock or desktop wake research mode.

1. `python3 -B profile_runner.py bootstrap` runs the application on a fresh directory, waits for exit and Xvfb retirement, then truncates the synthetic WAL. `make-seed` creates new synthetic data from only that schema; the helper verifies production encoding and normal mock validation/private session persistence. No real account or network is an input.
2. `qualify` checks the **original generator already writes a recency key**. `F` means the exact original generated `TEXT`, not missing history, a fresh OS page cache or an uncached Shelf. To obtain `R`, allow the real product to maintain a private independent copy normally; after its clean exit and WAL checkpoint, read just that one field. An extra ordinary launch without `--performance-trace` must produce the same bytes and correct Shelf. Do not transfer a post-start database or session to the trials.
3. Make two new copies of the original closed input and on each execute the same bound single-row update and checkpoint. Supply the original text to F, the product's actual text to R. Compare the parsed objects including ordered arrays, require the raw strings to differ and validate all other rows in every business table across both prepared copies. Other files (including covers and mock session) are independently copied from the same controlled source and never touched in this step. Do not export the strings, paths, files or accounts. Report only type/count/length/equality. A second launch against R must keep its genuine text. This protocol does not presume why the original representations differ.
4. The signed-out copy must prepare the same ten covers while displaying none of their marker codes. Separately run the cases with genuinely missing recency and with one disposable, unowned comic in an otherwise retained transient scope. The former must reconstruct and insert an equivalent record; the latter must delete the expendable membership/comic while preserving the original ten displayed covers, and must not rewrite compact recency. These setup cases are never included in the F/R statistics. The project's Rust tests separately exercise writer contention, rollback, protected owners and restoration.

## Fixed schedule and observables

`python3 -B profile_runner.py trial` runs once after qualification and explicit admission. Two excluded warmups `f00 r00` precede `f01 r01 r02 f02 f03 r03 r04 f04 f05 r05 r06 f06`. Every process gets an independent copied directory, Xvfb, home and default software renderer. No concurrent launches, locked shared database, forced wait or physical device. No dropping slow samples, replacements or extensions. The application executable inode is checked while its PID is live. Exact source arm and end-of-run diagnostic identity are tied to the same PID. A stopped schedule leaves its failure record and raw traces available for investigation.

Record one matched worker `state-cache-maintenance` parent begin/end pair and one `catalog_cache_maintenance` summary on the same thread, before state publication and software Ready. The summary is emitted **after** the end record: encoding and appending the summary do not count as parent work. Child operations report *durations* in microseconds on the worker, not individual absolute stage stamps. Process/worker/Ready timestamps use the application's actual monotonic nanoseconds. Normal completion, synchronous commit, timeout restoration and all twelve unique ordered phases are required for an admitted row-cost comparison. Four separate deletion counts, eviction candidates, durable IDs and upsert rows are distinguished. Setup requires F and R to have existing recency, 20 durable IDs, zero eviction/deletion rows, and upsert rows of 1/0 respectively. Preserve actual counts even when a hypothesis fails; a busy/error/partial result cannot be reclassified as a commit or substituted with another run. Timing gatekeeping is not an optimization decision.

`--capture final.png` is a private **end-of-run logical application snapshot**. On every positive launch, verify all ten pairwise-distinct cover marker codes are in their expected grid positions on Shelf page 1/2, plus ten resources/5,324,800 bytes at Ready, two attachment batches, the actual non-demo context and the ordinary route. This is not a first-visible image or an X11-to-panel measurement. No fixed minute, XGetImage polling, loading animation checks or new picture baseline are needed. Do not interpret normal variation in timing as a new faster implementation or promote counts to claims about disk flushes, physical writes or storage media.

`trial/projection.json` is the minimum structured output for independent timing analysis with `summarize_cache_profile.py PROJECTION`; use `--raw TRIAL` on the worker for direct cross-validation before deletion. It includes all fourteen cases, process/thread and software timestamps, the existing parent span, individual measured phase wall/CPU/row counts, committed/rollback status, and final fixture checks. Export no raw full JSONL, UI dump, images, database, saved identity, recency text, SQL or filenames from the profile. Remove the private workspace after independent review.
