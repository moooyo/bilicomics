# Off-device display-sampling baseline

Freeze this protocol before collecting results. The question is how much time the **unchanged** supervised startup display read spends in its outer shell, the actual Rust sampler and its owned child processes on Linux. It does not estimate a Kindle speedup. The archived Scribe result measures a different interval: 410 ms at the median from the launcher's go record to its observation of ready, not 410 ms of LIPC or permit checks. Use the [source replay](../startup-decisions-20261121/launcher-replay.md) for the physical intervals; never join its clocks to this experiment.

## Inputs and arms

- Use the exact stock `launch.sh` member of the retained installation ZIP. Run its actual `read_process`, group admission, watchdog, bounded pipe collector, poll loop, reaper, hex decoder and `capture_native_epdc_mode` functions in a fresh shell. A single transaction replaces everything before and after the sample. A private fixture supplies its ordinary generation, nonce and master PID files. The launcher creates its own read permission. Use the source-matched Rust `native_capture` and `native_presentation` modules, including the real `NativeReadPermit`, private files and Linux process ancestry. A small Linux executable replaces the product's outer CLI and hardware interfaces only. It never opens a framebuffer or invokes a real LIPC service.
- Each simulated property read runs a new executable with the production command arguments. Simulate active power and `Y8`; use a Scribe-shaped automatic-portrait metadata result with `L` normalized to `U`, and a PW6-shaped fixed-portrait result. These two geometries exercise different control paths, not hardware performance. Check that there are respectively five and three getter processes and two metadata samples per successful transaction. A helper implementing `usleep` honors the original durations; do not remove the 20 ms poll sleeps or the independent two-second watchdog.
- No authorization check is removed. Repeated permission checks read live process and lifecycle state; measuring their cost does not make them redundant. The candidate suggested for review has not qualified as equivalent. Run **A/A** with the identical stock code, build, seed and inputs for both labels. If a safe product change is later identified, freeze a separate one-factor comparison before executing it.

## Collection

1. Use only the network-isolated `test-env` Ubuntu userspace, no native input, firmware, credential, device connection or physical lease. Build a small host-only Release harness with the production `anyhow` and `libc` versions, offline, one Cargo job and a private target. No full application build is needed.
2. First qualify successful automatic and fixed responses. Also require inactive power at entry and exit, malformed mode, getter failure, timeout and permission revocation to fail closed or return the specified `not-active` result. Check that the admitted group is gone afterward. A rejected sample, including a timeout, must not become a timing success.
3. For each profile run two excluded warmups, then six A/A pairs in AB, BA, AB, BA, AB, BA order. Save every case. The primary elapsed time brackets one request to an already waiting shell and receipt of its exact parsed result. Use host `CLOCK_MONOTONIC`; shell startup, later process wait and fixture setup are outside the bracket. Within the bracket there are **no extra probes** in the sampler, permit or mock getter. Measure the empty request/response separately; do not subtract it. Do not replace failed cases or rerun for a different distribution.
4. In separate diagnostic passes (three per geometry), record the initial permit acquisition, subsequent permit rechecks, capture helper entry/return, and synthetic getter entry/return on the same Linux monotonic clock. Externally timestamp shell `begin`, `go`, `ready`, `reaped` and `parsed` notifications as they are read from a pipe. These are receive observations, not exact instruction timestamps. Keep the stock returned records and current-marker validation. The child entry/return interval excludes exec and shutdown. Time not explained by those timestamps includes spawning, loader/scheduling, pipe collection and polling; none of it is identified as pure fork or kernel cost.
5. Report the uninstrumented median and range per profile, differences for the identical arms, and individual diagnostic intervals/counts. Explicitly separate inclusive parent spans, nested waits and nonoverlapping permit samples. Do not add medians, subtract Linux values from the Kindle result, or claim that mock metadata/property timing measures drivers or on-device LIPC. The timing work finishes outside all device operations.

### Separate command attribution

After the baseline, freeze a further three diagnostic reads per profile, with a distinct output. Bracket the production `Commands::run` calls, `Command::spawn` in those calls, and only the permit rechecks invoked by the command runner. Do not remeasure the primary A/A series. These spans are nested: for each launch subtract the runner's context-check and spawn spans from its own inclusive wall time to locate the remainder (including actual getter execution, pipe reads, scheduling, polling and exit handling). A child may start before `spawn` returns, so do not subtract a child's body from the spawn or remainder. Do not introduce a poll wake, delay or altered permission test to expose these times.
